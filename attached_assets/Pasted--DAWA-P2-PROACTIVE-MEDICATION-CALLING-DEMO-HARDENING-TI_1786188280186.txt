========================================================
SCHEDULER
========================================================

Use APScheduler or another minimal in-process Python scheduler appropriate
for this single Replit deployment.

Do not create a distributed scheduler.

Create:

backend/app/services/scheduler.py

Responsibilities:

- inspect active medication schedules
- determine whether a dose is due
- create a dose_event idempotently
- enqueue/dispatch the call
- avoid duplicate calls for the same dose event
- update telephony state where appropriate

The scheduler must be isolated behind a small service interface so it can
be replaced later.

========================================================
IMPORTANT DEPLOYMENT LIMITATION
========================================================

Document clearly:

The in-process scheduler is suitable for this hackathon/demo deployment.

It is NOT claimed to be a production-grade durable scheduler across
multiple replicas or sleeping/restarting infrastructure.

Production could later use a durable scheduler/task queue.

Do not overengineer this now.

========================================================
DOSE EVENT IDENTITY
========================================================

A scheduled medication occurrence must have a deterministic identity.

For example conceptually:

patient_id
+
medication_id
+
scheduled local date/time

must uniquely identify one scheduled dose event.

Prevent duplicate DoseEvents when the scheduler scans repeatedly.

Example:

Razia
metformin-500
2026-08-08 21:00

should create exactly ONE dose event.

Repeated scheduler scans must not create another.

========================================================
SINGLE CALL CONCURRENCY
========================================================

Official Uplift hackathon calling supports only one outbound call in
progress per organization by default.

Design P2 around ONE active outbound call.

Implement a very small local dispatch lock / queue.

Do NOT use Redis.

When a due medication appears while another DAWA call is active:

- keep it queued/pending
- dispatch it after the active call becomes terminal

Do not fire simultaneous calls.

========================================================
RETRY POLICY
========================================================

Implement a small explicit retry policy.

Retry later for:

busy
no_answer
silent_pickup
voicemail
network_error

Do NOT immediately retry:

declined
wrong_number

For unreachable:

mark retryable-later but do not aggressively redial.

For hackathon demo:

maximum 1 automatic retry is enough.

Use a configurable short delay for demo mode.

Do NOT create infinite retry loops.
